# 미팅 메모 (10/5 월 10:00) — Defects4J Lang 생존 실험

Gary용. 교수님께 보내지 않음. 보고서: `docs/llm4ts-lang-survival-report.pdf`

## 내 말로 세 문장

1. 논문 데이터셋의 Lang 14개 클래스로 지난주 zod 생존 실험을 다시 했다. 논문의 다섯 프롬프트를 반복해서 LLM 테스트 수를 개발자 테스트 수 이상으로 맞췄다(1,353 대 703). 본문이 똑같은 중복 156개는 뺐다.
2. 버그를 고친 버전에서 개발자 테스트는 하나도 안 깨졌고 LLM 테스트는 22개가 깨졌다. 22개 전부 패치된 줄을 실행했고, 실패 메시지를 읽으면 19개는 버그 동작을 정답으로 단언한 테스트다(Lang-19의 9개는 "예외가 나야 한다"고 단언했는데 그 예외가 버그였다).
3. 그 뒤 버전들에서 개발자 테스트의 실패는 거의 전부 컴파일 실패(다른 클래스 API가 바뀜)이고, LLM 테스트의 실패는 전부 단언 실패다. LLM 테스트는 클래스 하나만 참조하기 때문에 컴파일은 되고, 깨지는 건 버그를 단언한 것들이다.

## 예상 질문과 답

**Q1. StringUtilsTest 같은 다른 클래스 테스트와 LLM의 클래스 테스트를 비교하는 게 맞나?**
Defects4J가 "수정된 클래스를 실행하는 테스트"로 지정한 `tests.relevant`를 썼고 지난주 zod도 프로젝트 전체 개발자 테스트였다. 같은 클래스 테스트(LookupTranslatorTest 등)만 세면 14개 레코드 합쳐 95개이고 측정 가능한 모든 시점에서 전부 살았다. 수가 적어 주 비교로 쓰지 않았고 저장소에는 있다. 대안으로 "CUT 코드를 실제로 실행하는 개발자 메서드"로 정의하는 방법이 있다(703개를 JaCoCo로 한 번씩 돌리면 됨).

**Q2. 논문 수치는 재현됐나?**
논문 모델 4개(GPT-3.5·GPT-4 초기 스냅샷, Mistral 7B, Mixtral)가 전부 API에서 내려가서 gpt-oss-120b로 바꿨다. 재현한 건 파이프라인(프롬프트 → 추출 → 컴파일 → 실행 → JaCoCo)이다. 저자 번들의 추출기 재구현이 코드 펜스를 불합격 처리하고 제네릭을 HTML로 오판해서 우리 규칙으로 바꿨다(70건 중 25 → 68 추출). 저자에게 알릴 것: 추출기 문제, 번들 ZSL.txt가 FSL 복사본, 결과 CSV 중복 행.

**Q3. LLM 생존율이 더 높은데 LLM 테스트가 더 튼튼하다는 뜻인가?**
아니다. 개발자 테스트 하락은 다른 클래스 API 변경에 따른 컴파일 실패 207건이고 단언 실패는 메서드 1개뿐이다. LLM은 클래스 하나만 참조해서 컴파일 실패가 0이다. 범위가 달라서 퍼센트를 직접 비교하면 안 된다. 보고서 표 2에서 실패 종류를 나란히 둔 이유다.

**Q4. 같은 프롬프트를 반복하면 같은 테스트가 나오지 않나?**
나온다. 본문이 글자까지 같은 것 156개(10%)를 뺐다. 이름이 같고 내용이 조금 다른 변형은 많다. 그것들이 서로 다른 동작을 검사하는지는 측정하지 않았다(한계에 적음). 측정하려면 메서드별 커버리지 비교가 필요하다.
